# Service Score — Technical Design Document (Phase 1)

**Jira:** IIRM-6282 · **Route:** `/my-client-portfolio` (iwork MFE) · **Backend:** policy-service, `service-tat` module
**Status:** Confirmed — implemented, since revised · **Last updated:** 2026-07-27
**Related:** [Service-Score-PRD.md](./Service-Score-PRD.md) — product-facing write-up of the calculation (weightages, TAT buckets, worked example)

This TRD covers computing a company's service score for a given financial year directly from source entities (endorsement, policy_claim, meeting, mir_report, opportunity_activity_map), plus the follow-on UI changes. It does **not** touch the two existing `/service-tat/*` endpoints — those stay as-is (per direction: "existing APIs keep as is").

> **2026-07-15 revision note:** D1–D21 below are the original design as first shipped (2026-07-14) — kept intact as the historical record. **D22 onward** capture what changed the next day: the dedicated `GET /service-tat/summary-details` endpoint this TRD originally specced was **removed** in favor of computing Service Score in a batch for the Client Portfolio listing's current page and embedding it in that response (§2, §4.1, §5.1 updated inline to match); an endorsement data-quality fix; a §10/`ServiceScoreDetails` column-consistency fix; and a weightage correction. Read D1–D21 as background on *why* the formula and scoping rules are what they are — read D22+ for the current endpoint shape.

> **2026-07-27 revision note:** **D26–D28** capture direct stakeholder feedback on Phase 1's live behavior: the month-level `scorePercentage` formula changed from a pooled raw-marks ratio to a weightage-based one (D26), the Client Portfolio listing and "View details" now resolve their months from whatever filter the caller has applied instead of always defaulting to the full financial year (D27), and a new Dashboard "Service Score" scatter-plot widget/endpoint was added (D28, additive — first appearance of Service Score outside Client Portfolio). §4.2/§4.3 updated inline to match; D17's original pooled formula and D22's "always full FY" behavior are both superseded — read D17/D22 as historical background only.

| D12 | Endorsement, Health Claims, and Non Health Claims are **policy-scoped**: first resolve the company's policies whose period overlaps the FY, then filter the source table by `policy_id IN (...)` — not by `company_id`/event-date directly. | D13 | Endorsement and Health/Non-Health Claims fully mirror the **validated `mir-report.service.ts` "Our Service Tracker" (s10) queries** rather than the originally-assumed `policy_type_segregation` join: (a) Endorsement = `endorsement` table (group policies) **+** `policy_asset_endorsement` table (non-group policies), summed; (b) Health/Non-Health classification is by `policy.policy_type_lid` matching an explicit `lookup_key` allowlist (`HEALTH_KEYS`/`NON_HEALTH_KEYS`), not `policy_type_segregation`; (c) claim TAT day-diff is `updated_at - created_at` (not `claim_dt - created_at`). | Stakeholder pointed at `mir-report.service.ts`'s `groupEndorsementTatQuery`/`nonGroupEndorsementTatQuery`/`claimsTatQuery` as the validated precedent to mirror exactly, after the policy-scoped endorsement/claims queries initially returned zero rows in testing. |
| D14 | The `lookup_data` join on `policy.policy_type_lid` (`ld.status = 1 AND ld.organisation_id = ...`) must compare against **the policy's own `organisation_id` column** (`ld.organisation_id = policy.organisation_id`), not the calling user's employee/org scope (`ScopeService` → `organisationId`). | Root cause of an "everything returns 0" regression: D13's join initially used the caller's resolved `orgId`, but that's a materially different value (broker employee's own org unit) from the policy's `organisation_id` (verified on `iirm_cust_ref_anon`: company 190550's policies + their `lookup_data.organisation_id` are consistently `1`, while `employee.organisation_id` varies — `1`, `2`, `3`, `5` — across users). | D15 | `getSummaryDetails`'s FY-month pre-seed (`monthServiceMap.set(month.key, new Map())` for all 12 months) must run **before** the event-processing loop, not after. | Root cause of the "still 0 after D14" regression: the loop's inclusion check (`if (!monthServiceMap.has(monthKey)) continue`) requires the 12 month keys to already exist. With pre-seeding placed after the loop, `monthServiceMap` was empty while the loop ran, so **every** event was silently dropped as "no month match" regardless of D12–D14 being correct. Verified live post-fix on `iirm_cust_ref_anon`: company 190550 FY2025-26 → `totalServiceScore: 56.43`, non-zero marks/events across 9 of 12 months. |
| D16 | `getSummaryDetails` fetches `mstr_tat_bucket`/`mstr_org_service_weightage` **without any org filter** — `findActiveTatBuckets()`/`findWeightages()` are called with `orgId` omitted, ignoring the caller's `ScopeService`-resolved organisation entirely for this lookup. `orgId` is still resolved and returned in the response as metadata, just not used to filter config. The caller's employee `organisation_id` can be `0` or any other value unrelated to that seed data (same root class of mismatch as D14), which would otherwise zero out every service's `weightage` and silently zero all marks regardless of D12–D15 being correct. Repository methods keep `orgId` as an *optional* param (old `/monthly-summary`/`/monthly-details` endpoints still pass it and are unaffected) — only the new endpoint omits it. **Caveat:** this only works because there is currently exactly one meaningfully-configured org (1); if/when a second org's TAT config is seeded, this will need to resolve the *right* org (e.g. from the company/policy's own `organisation_id`, mirroring D14) rather than dropping the filter entirely. |
| D17 | **Scoring formula corrected (final)** to match the stakeholder's worked example exactly — three distinct quantities per service per month, all three exposed in `details[serviceName]`: `totalMarks` = **Total** = Σ event count across all TAT buckets (raw request count, e.g. `35`); `scoredMarks` = **Scored** = Σ over every bucket of `(bucket event count × that bucket's own mstr_tat_bucket.tat_weight)` — a general weighted sum using each bucket's *actual* configured weight (not restricted to a single "fully compliant" bucket); `weightage_score` = **Weighted Score** = `totalMarks > 0 ? (scoredMarks / totalMarks) * mstr_org_service_weightage.weightage_score : 0` (the org-configured service weightage is used only as this multiplier, not exposed separately). Month-level `scoredMarks`/`totalMarks` are the **raw** sums of every service's `scoredMarks`/`totalMarks` (not the weighted `weightage_score`) — i.e. "of all logged requests across every service this month, what fraction landed in a weighted TAT tier." `indicator = resolvePerformanceIndicator(scorePercentage)` (>90 GREEN, >80 YELLOW, >70 ORANGE, else RED) — reused verbatim, replacing the static `"RED"` placeholder from D7. Field renamed `marks` → `scoredMarks` throughout (types, response DTO, `CompanyServiceScore` UI mapping). | First pass (superseded) assumed only the bucket with `tat_weight = 1` ever contributes and that `totalMarks`/`scoredMarks` were weightage-based. Stakeholder corrected with an exact worked trace on real output (`Endorsement, "46–1000 days": 35, rest 0` → `Total = 35`, `Scored = 1×0 + 0×0×4 + 0×35 = 0` since "0–7 days" is the only bucket with nonzero weight, `weightage_score = 0/35×4 = 0`) — confirming Total/Scored are the *raw request-count* quantities and `weightage_score` is the *only* place the org weightage multiplier appears. First live verification against `iirm_cust_ref_anon` (company 190550, FY2025-26) appeared to show the "0–7 days" bucket weight as `2` instead of `1`, producing `scorePercentage` over 100% in some months — this turned out to be **D18** (a duplicate-row double-count), not a real data value; see D18 and the corrected `totalServiceScore: 44.76`. |
| D18 | **Dropped `service_tat_score_map` (and `buildServiceBucketConfig`/`ensureServiceBucketMappings`) from `getSummaryDetails` entirely.** TAT bucket definitions now come straight and only from `mstr_tat_bucket` (`findActiveTatBuckets()`), converted once into a single shared `ServiceTatBucketConfig[]` applied uniformly to every service — no per-service override lookup. Weightages/services likewise come only from `mstr_org_service_weightage` / `mstr_service` directly, per stakeholder direction ("don't consider this table [service_tat_score_map] actually, you can rely on [mstr_service / mstr_org_service_weightage / mstr_tat_bucket] for calculation... refactor the entire function"). | Root cause of the "Scored is double" bug: `bucketConfigMap` (built by joining through `service_tat_score_map`) returned **two identical rows for the same `bucketId`** for at least one service (verified live — `serviceId 5` had `bucketId 1` duplicated in its config array), because `service_tat_score_map`'s `UNIQUE(service_id, tat_bucket_id)` constraint is declared inside `CREATE TABLE IF NOT EXISTS` in `service_tat_schema.sql` and is therefore never retroactively applied to a `service_tat_score_map` table that already existed without it (as is the case on `iirm_cust_ref_anon`) — so summing `count × tat_weight` over that array double-counted the bucket. Removing the `service_tat_score_map` join entirely (rather than de-duplicating its output) sidesteps the bad data altogether. Re-verified live post-fix: no more doubling (e.g. 21 events in "0–7 days" → `scoredMarks: 21`, not `42`); `totalServiceScore: 44.76`. The old `/monthly-summary`/`/monthly-details` endpoints still use `buildServiceBucketConfig`/`service_tat_score_map` unchanged — only `getSummaryDetails` was refactored off it. |
| D19 | **`details[serviceName]` gains a 4th field, `maxWeightage`** — the static `mstr_org_service_weightage.weightage_score` constant, distinct from `weightage_score` (which per D17 is the *computed* Weighted Score). UI: `ServiceScoreDetails` now maps "Max. weightage" → `maxWeightage` (previously null, since the static constant wasn't in the payload) and gained a new "Total marks" column mapped directly to `totalMarks` (previously only "No. of request", a client-recomputed value). | Stakeholder TODO-1: "add Total marks and Max weightage hold the weightage of service (mstr_org_service_weightage.weightage_score)" — the UI had nowhere to show the static per-service weightage once D17 repurposed `weightage_score` for the computed score. |
| D20 | **Health/Non-Health Claims classification reverted to `policy_type_segregation`** (undoing the D13 mir-report-mirrored `policy_type_lid` lookup_key-allowlist approach) — join `policy_claim → policy (policy_id) → policy_type_segregation (policy.policy_type_lid = pts.policy_type_lid) → lookup_data (pts.irdai_policy_type_lid = lookup_data.id)`, classify Health when `lookup_data.value IN ('Health','Life')`, else Non-Health. The static `SERVICE_SCORE_HEALTH_POLICY_TYPE_KEYS`/`NON_HEALTH_POLICY_TYPE_KEYS` allowlists (~65 `policy_type_lid` values copied from `mir-report.service.ts`) are removed, replaced by `SERVICE_SCORE_HEALTH_POLICY_TYPE_VALUES = ["Health","Life"]`. No new route — this is additive to the existing `/my-client-portfolio` → `CompanyOverView` → `CompanyServiceScore` → `ServiceScoreDetails` flow (`apps/ui/iwork/src/app/pages/ClientPortfolio/`). Changes there are in §5.

## 3. Data model

### 3.1 Existing master tables (reused, no changes)

- `mstr_service` (`ServiceMaster`) — 11 seeded services, `service_display_order` drives ordering.
- `mstr_org_service_weightage` (`OrgServiceWeightage`) — per-org, per-service weight. **Corrected per D25 — live-verified: sums to 100 across the 11 seeded rows for org 1** (this section originally said "sums to 1.0"; that was inaccurate — see D25 for the exact per-service values, also documented in the PRD §3).

### 3.3 Service → source-entity mapping (core calculation reference)

For every service, **TAT days = completion-date column − `created_at`**, then bucketed against the **single, shared `mstr_tat_bucket` list** (no per-service `service_tat_score_map` override — dropped per D18) using the same day-range matching / `resolveBucketLabel` logic as before.

**D12 — Two distinct scoping strategies, per stakeholder direction:**

1. **Policy-scoped** (Endorsement, Health Claims, Non Health Claims): first resolve the set of `policy` rows for the company whose policy period overlaps the requested financial year (`policy.company_id = :companyId AND policy.policy_from <= :fyEnd AND policy.policy_to >= :fyStart`), then filter the service's own table by `policy_id IN (...)` — **not** by the event's own date or by `company_id` directly. E.g. "FY 2025-26 for a company has 5 policies → check the endorsements in these 5 policies to calculate the TATs."
2. **Company-scoped** (MIR, all three meeting types, QCR Submission): filter directly by `company_id = :companyId` with no policy indirection — confirmed via the stakeholder's exact meeting SQL (`... and company_id=263681`) and "MIR — filter the MIR reports by companyId."

Of the 8 services with a defined computation in this phase, **3 are policy-scoped** (Endorsement, Health Claims, Non Health Claims) and **5 remain company-scoped** (MIR, Quarterly/Monthly/Multilateral Meeting, QCR Submission — QCR wasn't addressed in the policy-scoping clarification, so it stays scoped via `opportunity.company_id` as originally specified).

Policy-scoped queries also **drop the event-date range predicate** entirely (no `insurer_endorsement_date >= :start AND < :end` / event-date filter on claims) — inclusion is driven solely by policy membership in the FY, matching "check the endorsements in these five policies" literally. Each event is still bucketed into a specific month of the response using its own event date; an event whose date happens to fall outside the 12 target FY months simply won't match any month bucket and is dropped there (existing `getSummaryDetails` month-matching logic), so no separate SQL-level date filter is needed for correctness — only policy scoping determines inclusion.

**Per D14**, the policy-scoping subquery for Endorsement/Claims additionally requires `policy.policy_type_lid` to resolve to an **active `lookup_data` row for that same policy's own organisation** (`INNER JOIN lookup_data ld ON ld.id = policy.policy_type_lid AND ld.status = 1 AND ld.organisation_id = policy.organisation_id`) — note this is **not** the caller's `ScopeService`-resolved `orgId` (D14), it's a column-to-column comparison scoped entirely within the `policy`/`lookup_data` rows themselves. **Per D20**, Health/Non-Health Claims do **not** restrict this policy set further — the same FY-scoped policy list feeds both Endorsement and Claims; classification into Health vs Non-Health happens downstream via `policy_type_segregation` (see table below), not by narrowing which policies are fetched.

### 4.2 Response shape

Per **D17/D26 (final)** — supersedes the original draft below D7/D8. Shape is unchanged by D22/D27/D28 (still the same `SummaryDetailsData` object, found at `row.serviceScoreSummary` on each company in the listing response); **field semantics changed 2026-07-27 per D26/D27** (marked below):

```ts
interface ServiceScoreMonth {
  month: string;              // "2024-04" (sortable key)
  label: string;               // "Apr2024" (display label, per spec)
  scoredMarks: number;         // Σ of every service's raw scoredMarks (Scored) this month — unchanged, still raw
  totalMarks: number;          // Σ of every service's raw totalMarks (Total) this month — unchanged, still raw
  scorePercentage: number;     // D26: weightedScoreSum/weightageSum*100 (was scoredMarks/totalMarks*100)
  indicator: "GREEN" | "YELLOW" | "ORANGE" | "RED"; // resolvePerformanceIndicator(scorePercentage)
  details: {
    [serviceName: string]: {
      [bucketLabel: string]: number; // event count in that bucket, from mstr_tat_bucket (D8)
      scoredMarks: number;          // "Scored" = Σ(bucket event count * bucket.tat_weight), all buckets
      totalMarks: number;           // "Total" = Σ event count across all buckets (raw request count)
      weightage_score: number;      // "Weighted Score" = (scoredMarks/totalMarks) * mstr_org_service_weightage.weightage_score, or 0 — unchanged
    };
  };
}

interface SummaryDetailsData {
  orgId: number;
  companyId: number;
  financialYear: number;
  serviceScore: ServiceScoreMonth[]; // D27: months in the resolved {from,to} range when given, else all 12 FY months (unchanged fallback)
  totalServiceScore: number;         // D26: average(month.scorePercentage) across serviceScore[] (was Σmarks/Σtotal*100); NOT persisted (D3)
}
```

### 4.3 Calculation algorithm

For each month in scope — **D27:** the months spanning an explicit `{ from, to }` range when the caller supplied one (`buildMonthsInRange`), otherwise all 12 FY months as before (`buildFinancialYearMonths`) — per service in `mstr_service` (active):

1. Run its source-entity query (§3.3) scoped to `companyId`, using each row's day-diff to find its bucket in the single shared `mstr_tat_bucket` list (D18 — no per-service `service_tat_score_map` override). Source-event fetch itself is bounded to `[start, end]` of the resolved range (first/last month in scope), not always the full FY (D27).
2. `totalMarks` ("Total") = Σ event count across **all** buckets for that service this month.
3. `scoredMarks` ("Scored") = Σ over every bucket of `(that bucket's event count × that bucket's own tat_weight)` — a general weighted sum using each bucket's real configured weight, not restricted to any single bucket (D17).
4. `weightage_score` ("Weighted Score") = `totalMarks > 0 ? (scoredMarks / totalMarks) * mstr_org_service_weightage.weightage_score : 0`.
5. `details[serviceName]` = `{ ...bucketLabelCounts, scoredMarks, totalMarks, weightage_score }`. `buildServiceDetails` also accumulates `weightedScoreSum += weightage_score` and `weightageSum += maxWeightage` (the static per-service constant) across every service — new return values, per D26.
6. Month `scoredMarks`/`totalMarks` = Σ every service's raw `scoredMarks`/`totalMarks` (unchanged — still exposed on the month object for reference, but no longer used to derive `scorePercentage`, D26). **`scorePercentage` (D26, supersedes D17 step 6) = `weightageSum > 0 ? (weightedScoreSum / weightageSum) * 100 : 0`** — reconciles with the per-service Weighted Score/Max Weightage table (§5.2 of the PRD) by construction.
7. `indicator = resolvePerformanceIndicator(scorePercentage)` — reuses the existing method (`>90 GREEN, >80 YELLOW, >70 ORANGE, else RED`) verbatim, now against the D26 formula's output.
8. **`totalServiceScore` (D26, supersedes D17 step 8) = `average(month.scorePercentage for month in serviceScore[])`** — a straight arithmetic mean over whichever months D27 resolved into scope, **not** a re-pooling of raw marks across months (the old `Σ(month.scoredMarks)/Σ(month.totalMarks)×100`).

Per **D24**, steps 3/4/2/(the static weightage) surface in the UI as the standardized 4-metric pattern `Scored → Total Marks → Weighted Score → Max Weightage`, in that order, in both the Client Portfolio's `ServiceScoreDetails` table and the MIR report's §10 "Our Service Tracker". **Per D27**, `ServiceScoreDetails`'s "Max. weightage"/"Weighted scored" columns were also reordered (Max. weightage now precedes Weighted scored) — cosmetic, no formula impact.

### 4.3.1 Date-range resolution — `resolveSmartSearchDateRange` (D27, shared)

Both `PolicyService.getPortfolioCompanies` (Client Portfolio listing) and `PolicyService.getServiceScoreChart` (§4.5, D28) resolve their `{ from, to }` range through the same private helper, `resolveSmartSearchDateRange({ timeFilter, financialYear, period, fromDate, toDate })`:

1. If `timeFilter` (a quarter/month string) or `financialYear` is present → `getDateRangeWithoutTimestamp(timeFilter, financialYear)`.
2. Else if `period` is present → `getDurationDates(period)`, swallowing a thrown error and falling through to step 3 rather than propagating it.
3. Else if `fromDate`/`toDate` are present → use them directly.
4. Otherwise → both `from`/`to` are `undefined`, and downstream `computeSummaryDetailsForCompany` falls back to the full-FY behavior (`buildFinancialYearMonths`), matching pre-D27 behavior exactly.

`getServiceScoreChart` maps its own `quarter`/`month` query params onto this helper's single `timeFilter` slot (whichever of the two is provided; `month` takes precedence when both happen to be set, since it's passed first into the ternary-equivalent lookup — not expected in practice since the UI only sends one).

### 4.4 Scope / access

Same pattern as existing endpoints: resolve `orgId` via `ScopeService.getEmployeeDetails(userId)`, resolve accessible `companyIds` via `ScopeService.getNewEmployeeHierarchyByUserId` + `findCompanyIdsByUserIds`, reject with the existing "no access" warning-and-empty-result pattern if `companyId` isn't in the accessible set (or 403/400 — implementer's call, existing code silently returns empty rather than erroring; recommend keeping that behavior for consistency).

> **Per D22:** this section described the (now-removed) single-company endpoint's own access check. The batch `getSummaryDetailsForCompanies` does **not** re-check company accessibility itself — it trusts the `companyIds` it's given, which are exactly the companies `PolicyService.getAllPolicies`/`validateOpportunityScope` already scoped and authorized for the calling user when building the listing page. There is no separate authorization gate on the Service Score computation itself.

> ⚠️ **D28 gap:** `GET /policy/service-score` (§4.5) does **not** validate that `companyId` is one of the caller's accessible companies at all — `getServiceScoreChart`/`getServiceScoreChartData` compute and return the score for whatever `companyId` is passed, with no `resolveAccessibleCompanyIds`/`ScopeService` check in that path.
