# Centralized Report Export · PRD

**Module:** Centralized-Report-Export | **Apps:** iWork (SO Page, RO Page, Policy Page, BizDone) | **Date:** 2026-08-08 | **Status:** Draft

---

## Overview

Today, "generate a report in the background, poll it, and show it in a Downloads tray" exists in exactly one place: the BizDone Excel export (`user_bizdone_report` table, `policy-report-excel/export*` endpoints, `useReportExports` hook). Several other listing pages — Sales Opportunity (SO), Renewal Opportunity (RO), and the plain Policy listing — need the identical capability: apply filters, click Generate Report, keep working while it builds in the background, get notified and download it from a shared Downloads tray. This PRD defines a single, reusable async-export capability that any listing page in the application can adopt, instead of each page re-implementing its own job table and polling mechanism.

---

## Roles

| Role | System Identity | Action |
|---|---|---|
| Any authenticated iWork user with view access to a supported listing page (SO, RO, Policy, BizDone) | Existing per-page ACL/permission scope (no new permission model introduced) | Applies filters, clicks "Generate Report," views/downloads their own past exports from the Downloads tray |

This feature does not introduce new roles or permissions — it reuses whatever view/export access each host page already enforces before the export is enqueued (the export is scoped to what the requesting user is already allowed to see, matching the existing BizDone behavior).

---

## Scope

### In Scope
- One shared async export mechanism (enqueue → background generation → status poll → download) usable by SO, RO, Policy, and the existing BizDone report.
- Extending the existing `user_bizdone_report` table/job model (not replacing it) to carry a `reportType` per module instead of being BizDone-only.
- A single, unified "Downloads" tray in the frontend showing a user's exports across all modules, not one tray per page.
- Per-module report generation logic stays owned by the module that produces it (SO's export query lives in opportunity-service, Policy's in policy-service, etc.) — only the queueing/polling/state-machine plumbing is shared.
- Migrating the existing BizDone export onto the shared mechanism (as the reference implementation / first consumer of record).

### Out of Scope (Phase 1)
- Report *content* design for SO/RO exports (which columns, which filters) — that's each module's own spec, not this PRD's concern.
- Real-time push notification of export completion (e.g. websocket) — Phase 1 keeps the existing client-side polling model.
- Cross-service job execution (e.g. a single central worker generating every module's report) — deferred; each owning service runs its own worker against the shared table, consistent with how BizDone's worker already lives inside policy-service rather than a shared scheduler-service. Revisit if a genuine "reporting service" is proposed later.
- Retention/cleanup policy for old completed export files and job rows — deferred to a follow-up (flagged as an Open Question below).

## Lifecycle

Job state machine (per export request), unchanged from the existing BizDone behavior, now shared across all modules:

```
PENDING → PROCESSING → COMPLETED
                     ↘ FAILED
```

| State | Trigger | Behavior |
|---|---|---|
| PENDING | User clicks "Generate Report" on any supported page with filters applied | Job row inserted with `filtersApplied` + `reportType` (which module/report this is). Returned to the client instantly — never blocks on generation. |
| PROCESSING | Owning module's worker claims the job (atomic status-guarded claim; fire-and-forget trigger on enqueue, with a safety-net cron as backup) | Report is generated by replaying the stored filters through that module's own report-building logic; uploaded to S3 on success. |
| COMPLETED | Generation succeeds | `fileUrl` (backing `FileUpload` id) and `completedAt` set. Client's next poll / Downloads-tray refresh shows a ready-to-download entry. |
| FAILED | Generation throws | `errorMessage` set. Client is told the export failed and may retry (re-clicking Generate Report starts a fresh job — failed jobs are not auto-retried). |

**Dedup rule** (carried over from BizDone): if a user already has a `PENDING`/`PROCESSING` job with the *identical* filter set for the *same* `reportType`, a repeat click reuses that job instead of starting a duplicate.

## User Stories

**US-CRE-001**
As a user on the SO/RO/Policy listing page, I want to click "Generate Report" with my current filters applied so that I get an Excel export without waiting on the page or risking a timeout for large result sets.
- Traces to: BR-CRE-001, BR-CRE-002

**US-CRE-002**
As a user, I want a single "Downloads" tray that shows every report I've generated — regardless of which page I generated it from — so that I don't have to remember which page to go back to in order to download it.
- Traces to: BR-CRE-003

**US-CRE-003**
As a user, I want to be notified when my report is ready (or failed) even if I've navigated away from the page I generated it on, so that I don't have to keep that page open.
- Traces to: BR-CRE-004

**US-CRE-004**
As a developer adding export capability to a new listing page, I want to reuse the existing job-queue/polling/Downloads-tray plumbing so that I only need to write the report-generation query itself, not a new table, worker, and frontend polling loop.
- Traces to: BR-CRE-005

## Business Rules

**BR-CRE-001 — One job table, discriminated by report type**
All async exports (BizDone, SO, RO, Policy, and any future module) share the existing `user_bizdone_report` table. No new per-module tables are created. Each row's `reportType` column identifies which module/report it belongs to.

**BR-CRE-002 — Generation stays with the owning module**
The shared mechanism only owns the job lifecycle (enqueue, claim, complete, fail, dedup, pre-signed URL minting). The actual report-building query/Excel generation is implemented and owned by the service that produces that report type (e.g. opportunity-service for SO/RO, policy-service for Policy/BizDone) — never centralized into a single "does everyone's report generation" service.

**BR-CRE-003 — Downloads tray is global, not per-page**
The Downloads tray displays a user's export jobs across every `reportType` in one list, ordered newest-first. Listing (read-only) is served from wherever the shared table already lives — it does not require reaching into each owning module's internals, since listing is a plain query against the shared table.

**BR-CRE-004 — Fire-and-forget with a safety net**
Every enqueue immediately attempts generation in-process (no wait for a cron tick). A per-owning-module cron (mirroring the existing `ReportExportJobScheduler` pattern) runs on a short interval as a safety net only, to pick up jobs missed by a process restart and to recover jobs stuck in `PROCESSING` after a crash.

**BR-CRE-005 — No duplicate in-flight jobs**
A user cannot have two `PENDING`/`PROCESSING` jobs of the same `reportType` with identical `filtersApplied` — a repeat request is told the export is already in progress rather than starting a second one.

## Acceptance Criteria

**AC-CRE-001** (for US-CRE-001)
- Given a user is on the SO (or RO, or Policy) listing page with filters applied
- When they click "Generate Report"
- Then the request returns immediately with a job id and a "Preparing your report" toast, regardless of how many records match the filters

**AC-CRE-002** (for US-CRE-002)
- Given a user has generated reports from both the SO page and the Policy page in the same session
- When they open the Downloads tray
- Then both exports appear in one combined, newest-first list

**AC-CRE-003** (for US-CRE-003)
- Given a user generated a report and then navigated to a different page (still within the app)
- When that report finishes generating
- Then a toast notification appears and the Downloads tray's unseen-count badge increments, without the user needing to be back on the originating page

**AC-CRE-004** (for US-CRE-004)
- Given a developer is adding export capability to a new listing page
- When they wire up the shared hook/runner with their own report-generation callback
- Then no new database table, worker cron, or frontend polling logic needs to be written

## Data Contract

### Consumed
| Source Module | Data Needed | Purpose |
|---|---|---|
| Host page (SO/RO/Policy/BizDone) | Currently-applied filters (already-resolved, human-readable form — same shape as BizDone's `appliedFilters`) | Stored on the job row as-is; replayed by the owning module's generator when the job is claimed |
| Requesting user's session | `userId` | Scopes job ownership, dedup, and the Downloads-tray listing |
| Owning module's existing report/listing query | Whatever repository methods already back that page's synchronous listing/export today | Reused inside the module's own `generate(filters, userId)` callback — not re-implemented |

### Produced
| Data | Who Consumes It |
|---|---|
| Job row (`id`, `reportType`, `status`, `fileUrl`, `errorMessage`, timestamps) | The polling client (status check) and the Downloads-tray list endpoint |
| Generated Excel file (S3, registered as a `FileUpload` row) | End user, via pre-signed download URL minted fresh on every status/list read |

### Cross-Module Contracts to Raise
- Confirm with opportunity-service's team which repository/query already backs SO and RO's *synchronous* exports today (if one exists) — the async generator should replay that, not a new query, mirroring how BizDone's async path reuses `generateBizDoneExcelFromQuery`.
- Confirm the exact `reportType` enum values and naming convention before TRD locks them in, so they read consistently in cross-module tooling/logs (e.g. `SALES_OPPORTUNITY_LIST` vs `SO_LIST`).
